================================================================================
CENTRAL TUNNEL ENVIRONMENT — OAT TESTING PARAMETERS
================================================================================

World file        : central_tunnel.world (38.5 m × 17.5 m bidirectional corridor)
Agents            : 40 pedestrians (20 westbound, 20 eastbound)
Groups            : 5 dyads + 3 triads + 21 individuals
Configuration mode: 1 (BEH_CONF_CUSTOM) — YAML values used exactly as written
Launch file       : central_tunnel_no_robot.launch.py
Scenario directory: src/hunav_gazebo_wrapper/scenarios/domenic/central_tunnel/
Generator script  : src/hunav_gazebo_wrapper/scenarios/domenic/
                    generate_central_tunnel_yamls.py (seed = 42)
Duration per run  : 120 s, recorded at 10 Hz
Total runs        : 19 (3 baseline + 4 per phase × 4 phases)


--------------------------------------------------------------------------------
1. BASELINE PARAMETERS (per agent, seed = 42)
--------------------------------------------------------------------------------
Social force factor   : mean 11.58, range [7.06, 15.72]   (clamp [5.0, 20.0])
Goal force factor     : mean  3.42, range [2.51,  4.19]   (clamp [2.0,  5.0])
Obstacle force factor : mean 16.91, range [11.10, 24.64]  (clamp [2.0, 50.0])
Max velocity          : mean  1.28, range [1.04,  1.52]   (clamp [0.0,  1.8])
Goal distance         : ~30 m end-to-end traversal


--------------------------------------------------------------------------------
2. PHASE SCALING
--------------------------------------------------------------------------------
Each phase scales one parameter across every agent by a fixed factor. All
other parameters remain at baseline.

  Phase 1 — Social force     low ×0.55   high ×1.70
  Phase 2 — Goal force       low ×0.60   high ×1.60
  Phase 3 — Max velocity     low ×0.75   high ×1.25
  Phase 4 — Obstacle force   low ×0.50   high ×2.00

4. LAUNCH COMMANDS
--------------------------------------------------------------------------------
Run headless (gui:=false) when recording — the Gazebo client is GPU-intensive
with 40 agents and will distort the recording timing. Use the GUI only for
visual inspection.

  source ~/sfm_ws_fresh/install/setup.bash

  # Baseline (runs 1–3)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_baseline.yaml gui:=false

  # Phase 1 — social force low (runs 4–5)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase1_social_low.yaml gui:=false

  # Phase 1 — social force high (runs 6–7)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase1_social_high.yaml gui:=false

  # Phase 2 — goal force low (runs 8–9)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase2_goal_low.yaml gui:=false

  # Phase 2 — goal force high (runs 10–11)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase2_goal_high.yaml gui:=false

  # Phase 3 — speed low (runs 12–13)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase3_speed_low.yaml gui:=false

  # Phase 3 — speed high (runs 14–15)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase3_speed_high.yaml gui:=false

  # Phase 4 — obstacle force low (runs 16–17)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase4_obstacle_low.yaml gui:=false

  # Phase 4 — obstacle force high (runs 18–19)
  ros2 launch hunav_gazebo_wrapper central_tunnel_no_robot.launch.py \
    configuration_file:=domenic/central_tunnel/ct_phase4_obstacle_high.yaml gui:=false


--------------------------------------------------------------------------------
5. RECORDING (per run)
--------------------------------------------------------------------------------
In a second terminal, after the simulation has finished loading:

  source ~/sfm_ws_fresh/install/setup.bash
  python3 src/analysis/run_recording.py <run_id>

Output is written to:
  sim_results/central_tunnel/<phase_dir>/run_<run_id>/true_pos_.csv


--------------------------------------------------------------------------------
6. PER-PHASE ANALYSIS
--------------------------------------------------------------------------------
After all runs in a phase complete:

  python3 src/analysis/crowd_dynamics_evaluator.py \
    --custom-dataset run_1 sim_results/central_tunnel/central_tunnel_baseline/run_1/true_pos_.csv \
    --custom-dataset run_2 sim_results/central_tunnel/central_tunnel_baseline/run_2/true_pos_.csv \
    --custom-dataset run_3 sim_results/central_tunnel/central_tunnel_baseline/run_3/true_pos_.csv \
    --output-dir sim_results/central_tunnel/central_tunnel_baseline/analysis --dt 0.1

To regenerate every figure across all environments in one pass:
  bash regenerate_all_plots.sh


--------------------------------------------------------------------------------
7. NOTES
--------------------------------------------------------------------------------
• Configuration mode 1 ensures every YAML force-factor value is used exactly,
  so each phase varies precisely the intended parameter.
• Bidirectional flow creates head-on conflicts at the corridor mid-point,
  matching the ETH-Univ corridor topology.
• Group walking (dyads, triads) is implemented via the GroupWalkNode in the
  generated behaviour trees; group members share goals and walking pace.
• Known limitation: the SFM lacks path planning. Some agents are occasionally
  trapped by obstacle axis-aligned bounding-box forces near the corridor
  furniture — this appears as low path efficiency in the baseline metrics.
